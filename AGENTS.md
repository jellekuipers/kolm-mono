# kolm-mono

kolm-mono is a starter monorepo for proofs of concept. It's a working vertical slice:
a TanStack Start client and a Hono API with typed calls end to end, an MCP server,
validated environment config (varlock), and optional Postgres (Prisma) and
"Sign in with GitHub" (better-auth). Fork it and build the POC on top; favor a working slice over
completeness or polish.

## Layout

pnpm workspace (`apps/*`, `packages/*`, `tools/*`), managed through `vp` (Vite+). Internal
packages are consumed as TS source (`exports` pointing at `src/*.ts`), with no build step. `core` has no barrel: import each module by subpath (`core/notes`, `core/logger`), so the client can use the browser-safe ones (`core/notes`) without pulling in Node-only code (`core/logger`).

- `apps/server`: Hono on Node, on `API_HOST`:`API_PORT` (127.0.0.1:3000; loopback only by default, see Security). It runs directly from source with Node's type stripping (`node src/index.ts`, `--watch` in dev), so it has no build step or bundle.
  - `src/index.ts`: the entry point.
    - `import "varlock/auto-load"` comes first and loads and validates the env.
    - It then creates the optional services from `ENV`, serves the app (`@hono/node-server`), and shuts down gracefully, closing the database pool.
  - `src/app.ts`: `createApp(deps)` builds the app, and `AppType` is its type for `hono/client`.
    - `/api/*` routes are `@hono/zod-openapi` routes (`createRoute` + `.openapi(...)`), chained on one expression so `AppType` carries every route type. Spec at `/api/openapi.json`, docs (Swagger UI) at `/api/docs`.
    - `GET /api/health/live`: liveness. Always 200 while the process serves requests, with no dependency checks; point restart probes here.
    - `GET /api/health/ready`: readiness. Status, uptime and dependency checks: 200 when ok, 503 when a configured dependency (the database) fails. It also reports whether auth is configured (`checks.auth`). Point traffic and load-balancer checks here.
    - `GET /api/me`: the signed-in user, or 401. It's the example of a protected route.
    - `/api/auth/*`: better-auth's handler, mounted only when auth is enabled.
    - `GET/POST /api/notes`: the worked example (see Conventions). Reading is public; creating needs a session (401 otherwise).
    - `/mcp`: the MCP server. Browser requests need an `Origin` listed in `MCP_ALLOWED_ORIGINS` (comma-separated), as DNS-rebinding protection (those origins also get CORS headers and preflight answers); clients that send no `Origin` are always allowed.
  - `src/deps.ts`: `AppDeps`, the optional services (`db`, `auth`) and settings that `createApp` and `createMcpServer` receive, plus helpers that derive what a `core` function needs (`healthDeps`, `notesDeps`). `core` never imports `db`: the helper adapts the database to the narrow interface `core` declares.
  - `src/mcp.ts`: the MCP server (`@modelcontextprotocol/sdk`), Streamable HTTP, stateless, JSON responses. Each request gets a fresh server and transport. Tools get the app's `AppDeps` and are thin wrappers around `core` functions; the examples are `health` (the readiness report) and `list_notes` (the first tool with input).
  - `src/env.ts`: the typed `ENV` for the server's slice of the env schema. Generated by varlock; don't edit.
  - `src/errors.ts`: `ApiError(status, code, message)` for expected client-facing errors. `handleError`/`handleNotFound` answer every error as `{ error: { code, message } }`. Unexpected errors are logged and answered with a generic 500.
  - Middleware, in order:
    1. Request ID (`X-Request-Id`).
    2. One log line per request, with a request-scoped logger in `c.var.log`.
    3. Security headers (`hono/secure-headers`).
    4. Rate limiting (`hono-rate-limiter`): `API_RATE_LIMIT` requests per minute per client IP on `/api` and `/mcp`, answering 429 in the shared error shape. Health checks are exempt. The store is in memory, so limits are per process.
  - `vite.config.ts`: only tasks and test settings.
- `apps/client`: TanStack Start (React 19, React Compiler, Router, Query, SSR) on port 3001. `routeTree.gen.ts` is generated by the Vite plugin, so don't edit it by hand. Use the `#/*` import alias.
  - UI: Chakra UI v3 (`@emotion/react`) with its full default theme, so any Chakra component works without setup. Icons come from Phosphor (`@phosphor-icons/react`), which includes brand logos such as `GithubLogo`. Dark mode only: `<html className="dark">` in `routes/__root.tsx` plus `ChakraProvider` in `components/ui/provider.tsx`. There is no color-mode toggle and no `next-themes`. Tailwind is not used. The font is Inter (body and headings), loaded from Google Fonts in `__root.tsx`.
  - Env: `varlockVitePlugin` in `vite.config.ts`. `src/env.ts` is the typed `ENV` for the client's slice (generated). Only non-sensitive items may reach the browser, and varlock enforces that.
  - API calls: `getApi()` in `src/lib/api.ts` returns a `hono/client` typed from `server/app` (`import type` only; `server` is a devDependency). It has a 10 s timeout.
    - During SSR and in loaders, it calls the API directly at `API_URL` and forwards the user's `cookie` header, so server-rendered pages see the session.
    - In the browser, it calls same-origin `/api/*`. The catch-all server route `routes/api/$.ts` forwards those requests to `API_URL` (`lib/api-proxy.ts`), in dev and production alike.
      - It sets `x-forwarded-for` (from the socket, overwriting what the browser sent), `-host` and `-proto`, so better-auth's rate limiting sees the real client. Behind a reverse proxy, set `TRUST_PROXY=true` so the IP is read from the proxy's `X-Forwarded-For` instead of the socket (otherwise all users share the proxy's IP).
      - It answers 502 (in the same error shape) if the API is unreachable.
      - Auth routes go through it too, so auth cookies are first-party.
  - Data: define queries as `queryOptions` in `src/lib/queries.ts`, with every parameter in the `queryKey`. On a non-OK response, `throw await toApiError(res)` (`lib/api-error.ts`). Prefetch in the route `loader` with `context.queryClient.query(options)` and read with `useSuspenseQuery`, so pages server-render with data. The default `staleTime` is 30 s.
  - Pages:
    - `routes/__root.tsx`: the layout, with `components/app-header.tsx` (navigation, the signed-in user, sign in and out).
    - `routes/index.tsx`: the API's readiness and the signed-in user.
    - `routes/sign-in.tsx`: "Sign in with GitHub". It explains what to configure when auth is off, and returns the user to `?redirect=` (same-site paths only, `lib/redirect.ts`).
    - `routes/notes.tsx`: the worked example (see Conventions).
    - `routes/_authed.tsx`: a layout route that sends signed-out visitors to the sign-in page. Pages that need a user go in `routes/_authed/`, like `profile.tsx`.
    - `routes/_authed/profile.tsx`: the example form (TanStack Form with a Zod schema) that renames the user through better-auth.
  - Auth: `lib/auth-client.ts` is better-auth's React client (browser only, same-origin `/api/auth`). Use it for actions (sign in or out, update the user), and read the session with `meQueryOptions` (`/api/me`), so it also works during SSR.
  - SSR calls to the API forward the user's IP (`x-forwarded-for`) as well as cookies, so rate limiting is per user.
- `packages/core`: business logic shared by the API routes and MCP tools. Plain TypeScript and Zod.
  - `health.ts`: `getLiveness()`, and `getHealth({ pingDatabase? })` (readiness) with the `Liveness`/`Health` schemas. Checks time out after 2 s and never throw.
  - `notes.ts`: the worked example (see Conventions).
  - `logger.ts`: `logger` (configured by `LOG_LEVEL` and `LOG_FORMAT`) and `createLogger`.
- `packages/db` (optional): Prisma 7 with Postgres through `@prisma/adapter-pg`, plus a local Postgres (`compose.yaml`).
  - `prisma/schema.prisma` holds the schema, better-auth's tables and `Note` (the worked example). Migrations are in `prisma/migrations` (committed).
  - `prisma/seed.ts`: idempotent development fixtures (a demo user and two notes), run by `vp run db:seed`.
  - The client is generated into `src/generated` (gitignored) on install and by the cached `generate` task.
  - `src/index.ts`: `createDb(url)`, the `Db` type, and every generated model type.
  - Prisma's CLI and docker compose run through `varlock run` (tasks in `vite.config.ts`).
- `packages/auth` (optional): `createAuth({ db, secret, baseURL, github })`. That's better-auth with "Sign in with GitHub", the Prisma adapter, and the client IP read from `x-forwarded-for`, mounted at `/api/auth`. Exports the `Auth` and `AuthSession` types.
- `apps/e2e`: Playwright smoke tests against the running stack (`vp run e2e`). It starts `vp run dev` itself, or reuses one that's running. It isn't part of `ready`, and runs as its own CI job.
- `tools/tsconfig`: shared TS configs. Packages add `"tsconfig": "workspace:*"` as a devDependency and extend `tsconfig/node.json` (packages, server) or `tsconfig/react.json` (client). Strictness flags live in `base.json`.
  - `node.json` sets `erasableSyntaxOnly`, because Node runs that code directly. No `enum`, `namespace` or constructor parameter properties.

## Environment (varlock)

[varlock](https://varlock.dev) loads, validates and types the env. The varlock skill (`.agents/skills/varlock`) has the details.

- **`/.env.schema` is the single source of truth.** Every variable is declared there, with its type, default, description, and `@tag`s naming the packages that read it.
- **Each package that reads env imports its slice:** `apps/server/.env.schema`, `apps/client/.env.schema` and `packages/db/.env.schema` contain `@import(../../, pick=[#tag])`. The app schemas also generate a typed `ENV` (`src/env.ts`, `exposeEnv=local`). Read config through `ENV`, not `process.env`.
- **Where values go:**
  - Local values and secrets: root `.env.local` (gitignored).
  - Per-environment values: `.env.[APP_ENV]`, e.g. `.env.production`, committed.
  - Real environment variables always win.
- **Secrets:** encrypt local ones with `vpx varlock encrypt` (or set the value to `varlock(prompt)`), or reference a secret manager through a varlock plugin.
- **Validate** with `vpx varlock load` (masked) or `vpx varlock load --agent`.
- **Agents:** read and edit `.env.schema` and committed `.env.[env]` files only. Never read or write `.env`, `.env.local` or `.env.*.local`, and never echo secret values. Ask the user to set secrets.
- **Adding a variable:**
  1. Add it to `/.env.schema` with a description, a `@type` (unless it's a plain string), `@sensitive` if it's a secret, and a `@tag` per package that reads it.
  2. Read it via `ENV`. Running any varlock command regenerates `src/env.ts`.
- **How each process loads env:**
  - Server: `varlock/auto-load` (in dev and production).
  - Client: the Vite plugin. The built SSR server uses `ssrInjectMode: "auto-load"`, so it resolves env at startup, from its working directory, instead of baking values into the bundle.
  - Prisma and docker compose: `varlock run`.
  - Non-sensitive client values are inlined into the bundle at build time unless marked `@dynamic` (`API_URL` is).

## Optional services

The server always starts. Each optional service turns on when its environment variable is set:

| Service  | Enable with                                                                              | When it's off                                                           |
| -------- | ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Database | `DATABASE_URL`                                                                           | readiness reports `database: "disabled"`                                |
| Auth     | `BETTER_AUTH_SECRET`, `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` (needs the database) | `/api/auth/*` is 404, `/api/me` is 401, sign-in explains what's missing |

Local Postgres: `vp run db:up` (port `POSTGRES_PORT`, default 5432), then `vp run db:migrate` and optionally `vp run db:seed`.

GitHub OAuth app: create one per environment at https://github.com/settings/developers.

- Homepage URL: `BETTER_AUTH_URL`.
- Authorization callback URL: `<BETTER_AUTH_URL>/api/auth/callback/github`. In dev that's `http://localhost:3001/api/auth/callback/github`. Open the app on that same origin: `localhost` and `127.0.0.1` are different origins for cookies and better-auth's origin check.
- Put the client ID and secret in `.env.local`.

To add another provider, add it to `socialProviders` in `packages/auth`, add its env items, and add a button on the sign-in page.

To drop a service from a POC entirely, remove its package, its wiring in `apps/server/src/index.ts` and `app.ts`, and its items in `/.env.schema`.

Not done yet for auth (add it when a POC needs it):

- Roles and organizations (better-auth's `organization` plugin; the `organization-best-practices` skill covers it).
- Protecting `/mcp`, for example with better-auth's MCP/OAuth plugin. Until then, `/mcp` is unauthenticated: only expose read-only, non-sensitive tools.

## Conventions

**Worked example: notes.** A `Note` resource that touches every layer: anyone can read notes (database only), creating one needs a signed-in user. Copy its files when adding a feature:

- `packages/db/prisma/schema.prisma` (`Note`) and its migration `prisma/migrations/*_add_notes`, plus the demo notes in `prisma/seed.ts`.
- `packages/core/src/notes.ts`: Zod schemas, `listNotes`, and `NotesDeps` (the narrow data access that `core` takes instead of `db`). Tests with fake deps in `packages/core/tests/notes.test.ts`.
- `apps/server/src/deps.ts`: `notesDeps` adapts `AppDeps.db` to `NotesDeps`. `apps/server/src/app.ts`: `GET` and `POST /api/notes`, answering 503 `database_disabled` without a database. `apps/server/src/mcp.ts`: the read-only `list_notes` tool. Tests in `apps/server/tests/app.test.ts` and `mcp.test.ts`.
- `apps/client/src/lib/queries.ts` (`notesQueryOptions`), `apps/client/src/routes/notes.tsx` (loader prefetch, `useSuspenseQuery`, a create form for signed-in users that validates with the API's own `CreateNoteInput` from `core/notes`) and its link in `components/app-header.tsx`.

To delete it: remove those files and the notes parts of the files that stay, then delete the `Note` model and add a migration that drops the table (`vp run db:migrate`). The build regenerates `routeTree.gen.ts`.

Each convention below points at the example.

- **Adding an API route:**
  1. Put the logic in `core` (or a new package), so an MCP tool can reuse it. If it needs a service, take a narrow interface (like `NotesDeps`) and add a helper in `deps.ts` that derives it from `AppDeps`.
  2. Define the schemas with Zod and name the ones that matter with `.meta({ id: "Name" })` so they appear under `components.schemas`.
     - Don't use `.openapi()` on schemas defined outside the server. Zod 4 attaches it when a schema is created, so it only exists on schemas created after `@hono/zod-openapi` has loaded.
  3. Add a `createRoute(...)` in `apps/server/src/app.ts` (see the notes routes) and chain `.openapi(route, handler)` onto `api`. Request params, query and body are validated, and invalid input answers 400 (`code: "validation"`).
  4. Add a `queryOptions` in the client's `lib/queries.ts` (see `notesQueryOptions`).
- **Adding a page:** a file in `apps/client/src/routes/`, or in `routes/_authed/` if it needs a signed-in user (its `beforeLoad` puts `me` in the route context). Prefetch data in the `loader` and read it with `useSuspenseQuery`. `routes/notes.tsx` is the example.
- **Forms:** TanStack Form with a Zod schema as the `onChange` validator, Chakra `Field` components, and a Save button disabled until the form is valid and changed. `routes/_authed/profile.tsx` is the example, and `routes/notes.tsx` shows a create form.
- **Adding an MCP tool:** `server.registerTool(name, { description, inputSchema, outputSchema, annotations }, handler)` in `apps/server/src/mcp.ts`. Pass Zod shapes (`Schema.shape`), call into `core`, and return `structuredContent` along with a text `content` item. Tool arguments are untrusted input, the same as an HTTP request. A new service goes in `AppDeps` (`src/deps.ts`), which routes and tools both receive. `list_notes` is the example with input (a tool with a missing service returns `isError`, it doesn't throw).
- **Changing the database:** edit `packages/db/prisma/schema.prisma`, then run `vp run db:migrate` (creates a migration and regenerates the client). Keep better-auth's tables in sync with its config: plugins that add tables or fields need schema changes. `Note` and its migration are the example.
- **Secrets** never go in code, logs, errors or API responses. Mark them `@sensitive` in the schema; varlock then redacts them from logs and blocks them from client bundles.
- **Error handling:** in the server, throw `ApiError` for expected errors (validation, not found, unauthorized). Anything else becomes a logged 500 automatically; don't catch-and-log in handlers. Never put causes or internals in a response.
- **Logging:**
  - Use `c.var.log` in handlers and `logger` elsewhere, with a short constant message and context in fields (`log.info("user created", { userId })`). Don't interpolate values into the message, and don't add `console.log`.
  - Levels: `debug` for detail, `info` for normal events, `warn` for handled failures, `error` for bugs and 5xx.
- **End-to-end:** `apps/e2e/tests/*.spec.ts` (Playwright) checks that the running app works: SSR, the proxy, routing and env loading. Keep it to smoke tests with the default env; put logic in unit tests.
- **Tests** live in `<package>/tests/*.test.ts`, use `vite-plus/test`, and need no database or env:
  - Server routes and MCP: `createApp(deps).request(...)` with fake deps (see `tests/app.test.ts` and `tests/mcp.test.ts`). Keep `ENV` reads in `src/index.ts`, so the app stays testable.
  - Client server-side logic: pure functions with injected dependencies (see `tests/api-proxy.test.ts`).
- Import TS files with explicit `.ts` extensions in packages and the server (nodenext). The client uses bundler resolution and the `#/*` alias.
- Document exported APIs with short JSDoc (what it is, and any non-obvious contract). Use `//` comments for "why" inside code. Don't restate what the code says.
- **Dependencies:**
  - Pin every dependency version in the `catalog:` in `pnpm-workspace.yaml` (`catalogMode: prefer`), and reference it as `"catalog:"`.
  - Keep them on their latest versions (`pnpm outdated -r`). The exceptions:
    - Prisma stays on 7.x until 8 is released.
    - `@types/node` matches the Node runtime (24 LTS).
  - pnpm refuses versions published less than a day ago (`minimumReleaseAge`, a supply-chain safeguard). Don't add `minimumReleaseAgeExclude` entries: use the newest version that passes, and bump later.
    - If a too-new version is already in the lockfile, pnpm rejects it before re-resolving, even after you pin an older version. Workaround: add the exclusion for one install, so the lockfile is rewritten, then remove it and install again.
  - Dependabot (`.github/dependabot.yml`) proposes updates weekly, grouped, with a one-day cooldown and the exceptions above.
- **Vite+ tasks:**
  - The root config sets `run.cache: true`, so `package.json` scripts are cached too. Cached tasks replay their output and only see a filtered set of env vars.
  - Anything long-running or side-effectful (`dev`, `start`, `migrate`, `up`, ...) is therefore a task in that package's `vite.config.ts` with `cache: false`. Uncached tasks see the full shell env.
  - Root `package.json` scripts are the entry points (`dev`, `ready`, `test`, `db:*`, ...). They only call `vp run ...`, which Vite+ expands into the underlying tasks, so each keeps its own cache setting and env.
  - `vp run ready` is the gate: `db#generate`, then check, tests and builds. Each step is cached.
- Before finishing: `vp run ready`. A pre-commit hook runs `vp staged` (`vp check --fix`).

## Agent skills

Official vendor skills for the stack: Hono, better-auth, Prisma, MCP (`mcp-builder`), Chakra UI, React (`vercel-react-best-practices`) and varlock.

- They aren't committed: they're third-party content, and not all of it may be republished. `skills-lock.json` pins their sources and hashes, and `vp run skills` restores them into `.agents/skills/` (gitignored).
- `.claude/skills/` is committed, but only as links into `.agents/skills/`.
- Manage them with `vpx skills` (`npx` fails here because of `devEngines`):
  - `vpx skills update -p` updates them.
  - `vpx skills add <owner/repo> -s <skill> -a '*' -y` adds one, and updates the lock file. Prefer official vendor repos.
- They're excluded from `vp check`, so don't edit or format them.
- TanStack's skills ship inside its packages in `node_modules`.

## Security

- **The API trusts `x-forwarded-*`** (the client IP for better-auth). It listens on `API_HOST=127.0.0.1` by default, so only the client's `/api` proxy, which overwrites those headers, can reach it. Set `0.0.0.0` only behind a proxy that does the same.
- **`/mcp` is unauthenticated.** Only expose read-only, non-sensitive tools until it has auth.
- **Local Postgres** is published on 127.0.0.1 only. Its password is a public default.
- **Secrets:** the pre-commit hook runs `varlock scan --staged`, which blocks commits containing values of `@sensitive` items in plaintext.
- **`TRUST_PROXY`** (client, default `false`) makes the client trust `X-Forwarded-For` for the user's IP. Enable it only behind a proxy that overwrites that header, or users can spoof their IP.
- **Rate limiting:** per client IP on `/api` and `/mcp` (`API_RATE_LIMIT` a minute; the key is `x-forwarded-for`, else the socket address), plus better-auth's own limits on `/api/auth`. The store is in memory: with several API processes, use a shared store (hono-rate-limiter supports Redis).
- **Security headers** on every API response (`hono/secure-headers` defaults).
- **CI:** `.github/workflows/ci.yml` runs `vp run ready` and the e2e smoke tests on pushes to `main` and on pull requests.

## Known gaps

- There's no deploy target.
- Deploying needs the workspace source and `node_modules` (the server isn't bundled), plus the `.env.schema` files: varlock resolves env at startup.
- The client ships as one chunk of about 770 kB minified (227 kB gzip), over Rolldown's 500 kB warning, mostly because Chakra's full theme is included. Splitting vendor chunks would silence it.

# Using Vite+, the Unified Toolchain for the Web

This project is using Vite+, a unified toolchain built on top of Vite, Rolldown, Vitest, tsdown, Oxlint, Oxfmt, and Vite Task. Vite+ wraps runtime management, package management, and frontend tooling in a single global CLI called `vp`. Vite+ is distinct from Vite, and it invokes Vite through `vp dev` and `vp build`. Run `vp help` to print a list of commands and `vp <command> --help` for information about a specific command.

Docs are local at `node_modules/vite-plus/docs` or online at https://viteplus.dev/guide/.

## Built-in Commands vs Scripts

`vp <name>` runs a built-in command. `vp run <name>` runs a `package.json` script or a `vite.config.ts` task. Scripts cannot overwrite built-ins, so `vp dev` and `vp run dev` may do different things. Check `package.json` and `vite.config.ts` first, and run `vp run <name>` when the project defines a script or task with that name.

## Tool Versions

Run `vp toolchain` to show versions and relationships in the active Vite+
release. Add a tool name to select part of the graph. For example, run
`vp toolchain vite`. Use `--global` to ignore the local `vite-plus` package. Use
`vp why <package>` to show the package-manager dependency graph.

## Review Checklist

- [ ] Run `vp install` after pulling remote changes and before getting started.
- [ ] Run `vp check` and `vp test` to format, lint, type check and test changes.
- [ ] Check if there are `vite.config.ts` tasks or `package.json` scripts necessary for validation, run via `vp run <script>`.
- [ ] If setup, runtime, or package-manager behavior looks wrong, run `vp env doctor` and include its output when asking for help.
